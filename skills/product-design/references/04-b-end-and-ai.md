# B 端体验与 AI 交互专章

> 主要依据杨堃《决胜体验设计：AI 时代的 B 端用户体验设计指南》，辅以诺曼的认知框架与俞军的价值判断。
> 适用：B 端产品、SaaS、后台系统、企业内部工具、AI 原生或 AI 增强的产品。

---

## 一、B 端体验的三个前提

1. **客户 ≠ 用户。** 付费方、决策方、使用方、IT 维护方的诉求经常冲突。体验设计第一步不是画界面，而是画清「谁为谁买单、谁替谁承担后果」。
2. **场景 ≠ 功能。** 功能是系统的能力，场景是「谁在什么时候、为了什么、按什么步骤、遇到什么例外」。B 端的体验差距，多数不在功能多少，而在场景覆盖。
3. **体验 ≠ 界面。** 系统耦合、数据孤岛、权限混乱、信息断层，都会让界面「看起来还行，用起来要命」。B 端体验问题常常是**企业架构问题**的界面投影。

> 一句话：B 端体验是**业务链路、应用架构、数据架构、角色协作**的综合结果。

## 二、角色与画像

### 2.1 先分清两种画像

| 画像 | 描述对象 | 关键信息 | 用途 |
|---|---|---|---|
| 客户画像 | 组织/付费方 | 行业、规模、预算、采购流程、合规要求、ROI 诉求 | 判断值不值得做、怎么卖 |
| 用户画像 | 岗位/角色 | 职责、目标、KPI、权限、熟练度、使用频率、异常责任 | 判断怎么设计 |

**常见错误**：把客户画像当用户画像，结果做出一堆「老板喜欢、员工不用」的功能。

### 2.2 B 端用户画像的六个维度

| 维度 | 要问什么 | 对设计的影响 |
|---|---|---|
| 岗位职责 | 他为什么岗位负责？ | 决定任务与信息优先级 |
| 业务目标/KPI | 他被什么考核？ | 决定什么叫「有用」 |
| 系统熟练度 | 新手/熟练/专家？ | 决定信息密度、快捷方式、引导 |
| 使用频率 | 每天/每周/每月？ | 决定是否需要「记忆辅助」与「批量」 |
| 权限范围 | 能看什么、能改什么？ | 决定 IA 与操作可见性 |
| 异常责任 | 出问题谁处理？ | 决定告警、回溯、审计设计 |

**系统熟练度**是 B 端最容易被忽略的维度：同一个页面，新手需要解释与默认值，专家需要键盘流与批量操作。解决方式不是二选一，而是**渐进式披露 + 可配置**。

### 2.3 角色冲突的处理

| 冲突 | 典型表现 | 处理原则 |
|---|---|---|
| 付费方 vs 使用方 | 老板要报表，员工嫌填报麻烦 | 让填报产生即时价值（少填、自动带出、填完有反馈） |
| 管理者 vs 操作者 | 要留痕，操作者觉得被监控 | 留痕用于改进而非惩罚；可见范围透明 |
| 总部 vs 一线 | 标准化 vs 灵活性 | 标准化主流程，例外可申请、可配置 |
| 业务 vs IT | 快速上线 vs 稳定安全 | 分层：核心稳定、边缘可配置 |

## 三、用户调研：还原真实工作流

### 3.1 调研的四个目标

1. 理解业务：这个岗位到底在做什么、被什么考核。
2. 发现痛点：哪一步最烦、最容易出错、最耗时。
3. 验证假设：我们以为的问题，是否真实存在。
4. 评估方案：原型能不能被理解、能不能完成任务。

### 3.2 一对一访谈的十个锦囊

> 按书中命名，简要说明用途；具体话术需结合场景调整。

| 锦囊 | 作用 |
|---|---|
| 自我介绍法 | 降低戒备，说明来意与用途 |
| 激励动机法 | 让受访者愿意说真话（帮到他、影响产品） |
| 场景还原法 | 让用户讲「上一次」而不是「一般来说」 |
| 直击痛点法 | 追问最烦、最怕、最容易错的一步 |
| 总结过渡法 | 阶段性复述，确认理解，平滑转场 |
| 权威构建法 | 在专业话题上建立对话资格 |
| 回溯打断法 | 用户跑题时拉回关键节点 |
| 碎片重组法 | 把散落信息拼成完整流程 |
| 清晰主线法 | 围绕「目标-任务-障碍」推进 |
| 有始有终法 | 收尾确认、致谢、后续跟进 |

### 3.3 其他方法

| 方法 | 适用 | 注意 |
|---|---|---|
| 问卷 | 验证广度、量化分布 | 事实题与态度题分开设计 |
| 焦点小组 | 探索争议、收集语汇 | 容易被强势者带偏 |
| 可用性测试 | 验证「能不能用」 | 5 人可发现大部分严重问题 |
| 观摩实习 | 发现「说」与「做」的差距 | B 端最有效，成本也最高 |
| 数据分析 | 发现行为异常 | 需要口径与埋点 |

**B 端调研的核心**：不是问「你想要什么功能」，而是**还原真实工作流与例外**——谁在什么时候、用什么设备、按什么顺序、遇到什么异常、怎么绕过。

## 四、场景地图五步法

这是把「用户画像」变成「设计输入」的关键方法。

```
① 明确画像用户
      ↓
② 确定业务目标
      ↓
③ 推导关键任务
      ↓
④ 绘制旅程地图
      ↓
⑤ 细化业务场景
```

| 步骤 | 要做什么 | 产出 |
|---|---|---|
| ① 明确画像用户 | 选一个具体角色，不叠加 | 角色卡（职责/KPI/熟练度/权限） |
| ② 确定业务目标 | 这个角色要被考核的结果 | 目标清单（可量化） |
| ③ 推导关键任务 | 为达成目标，必须完成哪些任务 | 任务清单（动词开头） |
| ④ 绘制旅程地图 | 任务的时间顺序、触点、情绪、系统 | 旅程图（阶段/动作/痛点/机会） |
| ⑤ 细化业务场景 | 每个任务的前置条件、输入、异常、结果 | 场景卡（可进入设计） |

**场景卡的字段**：触发条件、角色、目标、前置数据、步骤、异常、成功标准、频率、失败代价。

**B 端与 C 端场景识别的差异**：

- B 端场景由**业务事件**触发（订单、工单、审批、盘点），C 端更多由**情绪/空闲**触发。
- B 端场景有**组织约束**（权限、合规、交接），C 端较少。
- B 端场景的「异常」往往比「正常」更常见，必须单独建卡。

## 五、产品定位与架构

### 5.1 避免「全家桶」

**症状**：一个系统服务所有角色、所有业务、所有地区；菜单越来越多，主路径越来越深。

**根因**：没有做子系统划分，用「加菜单」解决「加需求」。

**对策**：

| 划分依据 | 说明 | 例子 |
|---|---|---|
| 业务域 | 按业务能力拆 | 订单、库存、结算 |
| 角色 | 按使用主体拆 | 商家端、运营端、管理端 |
| 生命周期 | 按数据/流程阶段拆 | 售前、履约、售后 |
| 变更频率 | 稳定的与多变的分离 | 核心交易 vs 活动配置 |

### 5.2 信息架构与菜单

- 按**任务/对象**分类，不按部门/技术分类。
- 一级菜单 ≤ 7 个；超过就说明需要分层或拆系统。
- 菜单名用**用户的工作语言**，不用内部术语。
- 高频任务放一级，低频配置放二级；不要为了「整齐」牺牲可达性。

### 5.3 企业架构视角

B 端的很多体验问题，根因在应用架构与数据架构：

- 同一数据在多个系统重复维护 → 用户要填多遍。
- 系统间无集成 → 用户要在多个窗口切换、手工搬运。
- 权限模型粗放 → 要么看不到，要么全可见。
- 主数据不一致 → 报表对不上，用户不信任。

**设计前的三个问题**：数据从哪来？系统边界在哪？谁是主数据源？

## 六、设计价值观与原则

### 6.1 「像管家一样贴心」

杨堃提出的设计价值观，可以拆成四个可执行的动作：

| 价值观 | 可执行动作 |
|---|---|
| 预判需求 | 默认值、智能带出、下一步推荐 |
| 减少操作 | 批量、快捷方式、复制上一单、自动保存 |
| 兜住异常 | 失败可恢复、离线可继续、超时提醒、数据校验 |
| 不添麻烦 | 少弹窗、少必填、少跳转、少重复录入 |

### 6.2 设计原则的写法

坏原则：「简洁、高效、易用」——正确但不可执行。
好原则：「一屏只回答一个任务；异常固定位置；批量操作不超过三步；所有提交可撤销」。

原则要能**指导取舍**：当两个方案冲突时，原则能告诉你选哪个。

## 七、页面范式

### 7.1 信息框架

| 形态 | 适用 | 要点 |
|---|---|---|
| 融合 Agent 的首页 | AI 能力已具备，用户需要入口 | Agent 作为「副驾驶」而非替代 |
| Agent 侧边栏 | 用户在主界面工作时需要随时问 | 不打断主流程，可折叠 |
| 信息流首页 | 需要感知动态、待办、异常 | 按重要性排序，不是按时间 |
| Agent 与全局搜索 | 找东西、问问题 | 搜索即入口，结果可直接操作 |

### 7.2 工作台四步法

| 步骤 | 动作 | 输出 |
|---|---|---|
| ① 明确画像用户 | 这个工作台给谁用？ | 一个角色，不叠加 |
| ② 梳理工作事项 | 他每天/每周要处理什么？ | 事项清单（频率/紧急度/价值） |
| ③ 选择呈现组件 | 每个事项用什么组件？ | 指标卡/列表/待办/图表/快捷入口 |
| ④ 设计工作台 | 排序、分组、层级、刷新 | 一屏内可完成最高频的 3 件事 |

**检验**：用户早上打开工作台，能否在 10 秒内知道「今天先做什么」？

### 7.3 表单、列表、详情

| 页面 | 核心目标 | 设计要点 |
|---|---|---|
| 表单 | 降低填写成本与错误 | 分组、默认值、校验时机、草稿、批量导入 |
| 列表 | 快速扫描与批量处理 | 列的可配置、筛选、排序、批量操作、空态 |
| 详情 | 快速理解与决策 | 关键信息前置、状态可见、操作聚合、关联数据 |

**B 端页面的本质**：不是「展示信息」，而是「处理工作任务」。判断标准是「用户能不能在这里把事做完」，而不是「信息是否齐全」。

### 7.4 ChatBI 与 Data Agent

- 适合：探索性查询、口径解释、异常归因、生成图表。
- 不适合：高精度对账、强合规报表、需要固定口径的考核数据。
- 设计要点：展示查询口径、允许追问、结果可导出、错误可纠正。

## 八、微交互三系统

### 8.1 反馈系统

**目标**：让用户在任何时刻都知道「发生了什么、系统在什么状态、下一步做什么」。

| 提醒程度 | 适用 | 例子 |
|---|---|---|
| 静默 | 成功、状态变化 | 行内勾选、进度条、状态标签 |
| 提示 | 需要注意但不阻断 | 行内提示、toast、角标 |
| 阻断 | 高风险/不可逆 | 弹窗确认、二次验证 |

**场景四问**：

1. 谁需要知道？
2. 多快需要知道？
3. 不知道会怎样？
4. 知道了要做什么？

**四个设计要点**（实践总结）：

- 反馈要**具体**：「保存成功」不如「已保存 3 条，2 条待同步」。
- 反馈要**可行动**：告诉用户下一步，而不只是告知结果。
- 反馈要**一致**：同一类状态用同一位置、同一颜色、同一语气。
- 反馈要**分层**：不要用弹窗处理所有事情。

### 8.2 促活系统

**目标**：让新用户上手、让老用户发现、让用户学会、让行为纠偏。

| 场景 | 手段 | 注意 |
|---|---|---|
| 上手引导 | 任务式引导、示例数据、模板 | 不要 8 步弹窗；让用户在做中学 |
| 功能发现 | 场景化推荐、空态提示、更新日志 | 在用户需要时出现 |
| 深度学习 | 帮助中心、案例、进阶技巧 | 与任务绑定，不做说明书 |
| 行为纠偏 | 校验、提示、最佳实践建议 | 先防错，再提示 |

**判断标准**：引导是否让用户**完成了一个真实任务**，而不是「看完了」。

### 8.3 消息系统

| 渠道 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| 站内信 | 可控、可追溯 | 需用户主动看 | 系统通知、审批、任务 |
| 移动端 Push | 触达快 | 易打扰、可关闭 | 紧急待办、异常 |
| 第三方 IM | 融入工作流 | 依赖外部、难管理 | 团队协作、提醒 |
| 短信/电话 | 强触达 | 成本高、扰民 | 高危、验证码、紧急 |
| 邮件 | 正式、可存档 | 打开率低 | 报表、合同、周报 |

**选择原则**：按「紧急度 × 用户成本 × 可达性」选，不要所有消息都走最强渠道。

**消息设计四问**：谁需要？多紧急？他现在能处理吗？不处理会怎样？

## 九、AI 时代的人机交互：六脉神剑

> 杨堃原创框架。核心不是「加一个聊天框」，而是先判断任务，再选择交互形态。

### 9.0 剑鞘：任务分诊

先用二维四象限给任务分类（书中以任务特征分诊），回答三个问题：

1. 这个任务**结构化程度**如何？（规则明确 vs 需要判断）
2. 这个任务**复杂度/风险**如何？（低风险 vs 高后果）
3. 用户希望**主动发起**还是**被动接收**？

分诊结果决定：

| 任务类型 | 推荐形态 |
|---|---|
| 高频、低复杂度、查询类 | 全局搜索 / 快捷指令 / Chat |
| 高频、结构化、编辑类 | Copilot（嵌入式建议） |
| 低频、高复杂度、多步骤 | Agent（人确认后执行） |
| 低频、低复杂度、一次性 | 传统 GUI 即可，不必 AI |

**一句话**：不是所有任务都值得 AI 化；AI 化之前先问「它替用户省了哪一步」。

### 9.1 第一剑：封装 API

- 把系统能力变成 AI 可调用的**原子能力**：查订单、改地址、建工单、发通知。
- 没有 API，AI 只能「陪聊」，不能「办事」。
- 设计要点：权限、幂等、审计、失败回滚。

### 9.2 第二剑：CUI 嵌入 GUI

- 不要另起一个孤立的聊天页；把对话嵌进用户正在工作的界面。
- 形态：侧边栏、首页卡片、全局搜索、表格行内助手、详情页 Copilot。
- 原则：**对话是手段，完成任务是目的**；不要让用户「离开工作现场去聊天」。

### 9.3 第三剑：Chat

- 用户主动提问，AI 回答/执行。
- 适合：探索、查询、解释、生成、跨系统操作。
- 设计要点：意图识别、澄清追问、结果可执行、错误可纠正、上下文可见。

### 9.4 第四剑：Copilot

- AI 在用户工作流中**主动建议、补全、预填**。
- 适合：结构化任务、表单填写、文案/代码/报表、决策辅助。
- 设计要点：建议可忽略、可修改、可追溯；不要抢用户的控制权。

### 9.5 第五剑：Chat 拆主动/被动

| 模式 | 说明 | 例子 |
|---|---|---|
| 被动 Chat | 用户问，AI 答 | 问答、查询、解释 |
| 主动 Chat | AI 主动推送 | 异常预警、机会提醒、待办催办 |

主动 Chat 的风险是打扰与误判，必须有**频率控制、可信度标注、关闭入口**。

### 9.6 第六剑：Copilot 拆主动/被动

| 模式 | 说明 | 风险 | 设计 |
|---|---|---|---|
| 被动 Copilot | 用户操作，AI 建议 | 低 | 可忽略、可修改 |
| 主动 Copilot | AI 自动执行 | 高 | 人确认、可撤销、可审计 |

### 9.7 人在回环的两种协同

| 模式 | 说明 | 适用 |
|---|---|---|
| AI 建议，人确认 | AI 给出方案，人决定 | 高风险、不可逆、合规场景 |
| 人操作，AI 辅助/接管 | 人主导，AI 补全/代办 | 高频、低风险、可撤销 |

**红线**：涉及金钱、权限、对外承诺、医疗/法律建议，必须保留确认、撤销、追溯。

### 9.8 集齐六剑的顺序

```
任务分诊 → 封装 API → 决定嵌入位置 → 选 Chat/Copilot → 拆主动/被动 → 设计人在回环 → 定度量
```

跳过任何一步，都会得到「 demo 很惊艳、上线没人用」的 AI 功能。

## 十、AI 产品设计检查清单

- [ ] 这个任务真的需要 AI 吗？传统 GUI 是否更便宜、更可靠？
- [ ] AI 替用户省了哪一步？是输入、判断、操作，还是等待？
- [ ] 能力是否封装成可调用、可审计的 API？
- [ ] 交互形态是 Chat、Copilot、Agent，还是嵌入现有界面？为什么？
- [ ] 用户能否看懂 AI 的依据/来源/置信度？
- [ ] 错误时能否纠正、撤销、转人工？
- [ ] 高风险动作是否有人确认与审计？
- [ ] 首次使用是否在 30 秒内展示价值？
- [ ] 是否有「不用 AI」的路径？
- [ ] 度量是否包含任务完成率、采纳率、回退率、人工接管率？

## 十一、体验度量

### 11.1 经典模型

| 模型 | 测什么 | 适用 |
|---|---|---|
| SUS | 整体可用性 | 跨产品对比 |
| NPS | 推荐意愿 | 客户关系、品牌 |
| CSAT | 满意度 | 单次体验 |
| CES | 费力度 | 服务/流程 |
| PULSE | 页面级行为 | 流量型产品 |
| HEART |  Happiness/Engagement/Adoption/Retention/Task success | 通用体验框架 |
| GSM | Goal-Signal-Metric | 把目标落成指标 |

### 11.2 国内模型

| 模型 | 来源 | 特点 |
|---|---|---|
| 五度模型 | 阿里 1688 | 多维体验评估 |
| UES | 阿里云 | 云产品体验度量 |
| PTECH | 蚂蚁 | 技术+体验结合 |

### 11.3 B 端选型建议

优先顺序：

1. **任务效率**（时长、步骤、一次成功率）——最贴近业务。
2. **错误与返工**（错误率、工单量、整改时长）。
3. **采纳与留存**（功能采纳率、席位留存、续费）。
4. **满意度**（CSAT/NPS）——作为交叉验证，不作唯一依据。

### 11.4 AI 产品度量

| 维度 | 指标 |
|---|---|
| 效果 | 任务完成率、准确率、幻觉率 |
| 采纳 | 建议采纳率、修改率、忽略率 |
| 信任 | 回退/撤销率、人工接管率、可解释满意度 |
| 效率 | 完成时长、步骤减少、等待时长 |
| 成本 | token 成本、延迟、运维 |

### 11.5 度量误区

- 只用 NPS：样本少、决策链长，解释力有限。
- 只测「满意度」不测「任务成功」：用户可能「满意但没用成」。
- 口径不一致：不同团队各算各的，无法比较。
- 只在上线前测：体验是持续过程，需要常设指标。

## 十二、B 端案例：连锁门店巡检

### 12.1 角色与冲突

| 角色 | 诉求 | 冲突 |
|---|---|---|
| 店长（使用者） | 快、少填、别老弹窗 | 与总部「留痕」要求冲突 |
| 区域经理（管理者） | 看到真实情况、异常闭环 | 与店长「怕被罚」冲突 |
| 总部运营（客户/决策） | 标准化、可比、可分析 | 与一线「灵活性」冲突 |
| IT | 稳定、权限、集成 | 与业务「快上线」冲突 |

### 12.2 场景地图（节选）

| 步骤 | 内容 |
|---|---|
| 画像用户 | 店长，系统熟练度中等，每天开店前 30 分钟 |
| 业务目标 | 门店合规率、异常整改率 |
| 关键任务 | 按清单检查、拍照、上报异常、跟进整改 |
| 旅程 | 开店准备 → 逐项检查 → 拍照 → 提交 → 处理异常 |
| 场景细化 | 离线、照片不合格、跨店代班、重复提交、整改超时 |

### 12.3 设计要点

- **工作台**：店长打开即看「今日待巡检 + 待整改」，10 秒知道先做什么。
- **表单**：按区域分组，默认值（门店/日期/巡检人），拍照即校验（模糊/缺角度）。
- **离线**：本地暂存，恢复网络自动同步，状态可见。
- **异常**：不合格项自动生成整改单，指派责任人，超时升级。
- **反馈**：提交成功、待同步、照片不合格，分别用不同层级。
- **消息**：整改超时 → 店长站内信 + 区域经理日报；不用短信轰炸。
- **度量**：巡检完成率、漏项率、整改闭环时长、一次通过率、区域排名。

### 12.4 常见失败

- 只做「填表」，不做「整改闭环」→ 数据有了，问题没解决。
- 只做「总部看板」，不做「店长效率」→ 一线抵触，数据造假。
- 强制拍照定位，不考虑代班/离线 → 流程走不通。
- 用 NPS 评估，不看漏项率与闭环时长 → 度量失真。
