# 八步工作流操作手册（P0–P7）

> 这份手册把 SKILL.md 的骨架展开成可以照着做的动作。
> 用法：完整项目按 P0→P7 走；快速模式只走 P0、P2、P3 的概念模型、P6 的验证设计。
> 每个阶段都给出：目的、动作、提问脚本、产出、常见错误、退出检查。

---

## 时间盒建议

| 阶段 | 完整项目 | 快速模式 | 备注 |
|---|---|---|---|
| P0 立题 | 0.5–1 天 | 15 分钟 | 与业务方/用户一起做 |
| P1 见人 | 3–10 天 | 跳过或 1 小时 | 取决于能否接触到真实用户 |
| P2 算账 | 0.5–1 天 | 20 分钟 | 先粗后细 |
| P3 建模 | 2–5 天 | 1 小时 | 与设计/研发一起 |
| P4 行为 | 1–3 天 | 30 分钟 | 仅高频产品需要 Hook |
| P5 感知 | 2–5 天 | 随原型 | 与视觉/文案一起 |
| P6 验证 | 1–2 周 | 30 分钟定计划 | 可用性测试至少 5 人 |
| P7 交付 | 持续 | 随方案 | PRD 与评审 |

## P0 立题：把「想法」还原成「问题」

### 目的

在投入任何设计之前，确认「我们解决的是真问题，而不是一个被伪装成问题的方案」。

### 动作

1. **写问题陈述**（一句话，严格按句式）：

   ```
   [角色] 在 [场景/触发] 下，想 [目标]，
   但 [障碍]，目前只能 [替代方案]。
   ```

2. **写三条非目标**：这次明确不解决什么。非目标不是「以后再说」，而是「这次做了会分散资源」。

3. **判定产品类型**，因为它决定后面用哪些镜头：

   | 类型 | 特征 | 主用镜头 |
   |---|---|---|
   | C 端高频 | 每天/每周多次，情绪驱动 | 埃亚尔 + 诺曼 + 原研哉 |
   | C 端低频 | 每月/每年少数几次，任务驱动 | 诺曼 + 俞军 |
   | B 端工作流 | 角色多、权限复杂、异常多 | 杨堃 + 诺曼 |
   | 平台/交易 | 双边或多边，网络效应 | 俞军 + 杨堃 |
   | AI 原生 | 能力不确定、交互范式未定 | 杨堃（六脉神剑）+ 诺曼 |

4. **写「为什么是现在」**：技术变化、政策、用户行为迁移、竞争。写不出来，说明可能不是现在该做的事。

### 提问脚本

- 「如果不做这个，用户现在会怎么做？会损失什么？」
- 「这个问题，用户自己会怎么描述？会用我们的词吗？」
- 「如果只能解决一个场景，你选哪个？为什么？」
- 「这件事不做的代价是什么？谁承担？」

### 产出

`assets/design-brief.md` 的第一部分：问题、角色、场景、非目标、类型、时机。

### 常见错误

- 问题陈述里出现「做一个 XX 功能」——这是方案，不是问题。
- 把「用户想要」当「用户需要」——用户说的是解决方案，不是问题。
- 非目标写成「暂不支持」——那是范围，不是取舍。

### 退出检查

- [ ] 问题陈述里没有功能名
- [ ] 能说出三个非目标
- [ ] 能说出「为什么是现在」
- [ ] 用户/业务方能复述你的问题定义，且没有异议

## P1 见人：把「用户」拆成角色 × 场景 × 任务

### 目的

把抽象的「用户」变成具体的「谁、在什么时候、做什么、被什么卡住」。

### 动作

1. **拆角色**（B 端必做）：

   | 角色 | 关心什么 | 典型诉求 | 典型阻力 |
   |---|---|---|---|
   | 使用者 | 省事、少出错、快 | 批量、快捷键、默认值 | 学习成本、迁移麻烦 |
   | 购买者/客户 | 成本、合规、ROI | 报表、审计、集成 | 预算、采购流程 |
   | 决策者 | 风险、战略、政绩 | 可视化、对标 | 怕担责、怕变化 |
   | IT/运维 | 稳定、安全、可维护 | 权限、日志、SSO | 集成复杂度 |
   | 影响者 | 专业意见、口碑 | 试用、案例 | 谨慎、怕背锅 |

2. **拆场景**：触发条件、时间地点、设备、情绪、前后动作、成功标准。

3. **画现状旅程**：把替代方案画进去——Excel、微信群、纸质表单、人工、外包、什么都不做。**替代方案就是「旧体验」的实体**。

4. **标断点**：按「频率 × 痛感 × 价值」排序，选出 3 个。

### 提问脚本

- 「上一次你做这件事是什么时候？能从头到尾讲一遍吗？」（场景还原）
- 「哪一步最烦？烦在哪？你当时怎么绕过它？」（直击痛点）
- 「如果今天系统坏了，你会怎么完成工作？」（替代方案）
- 「这件事做错了会怎样？谁会发现？谁负责？」（异常与责任）
- 「你一天要在这上面花多久？一周几次？」（频率与成本）

### 产出

角色-场景-任务表：

| 角色 | 场景/触发 | 任务 | 当前替代 | 痛点 | 频率 | 失败代价 |
|---|---|---|---|---|---|---|
| 店长 | 每日开店前 | 检查设备与陈列 | 纸质清单 | 漏项、无法追溯 | 每天 | 中 |
| 区域经理 | 每周巡店 | 抽查 5 家店 | Excel + 微信 | 数据滞后 | 每周 | 高 |

### 常见错误

- 用人口属性代替角色：「25–35 岁女性」不能指导设计。
- 只访谈「友好用户」，忽略反对者与异常场景。
- 把「客户」当「用户」，把「老板需求」当「用户需求」。
- 忽略「什么都不做」这个最强的竞品。

### 退出检查

- [ ] 每个核心场景都能落到「具体的人 + 具体时间 + 具体替代动作」
- [ ] 至少识别出 1 个「客户/用户/决策者」冲突
- [ ] 断点按频率与痛感排了序，而不是按声音大小

## P2 算账：价值与交易

### 目的

判断「值不值得做」，以及「用户为什么会换」。

### 动作

1. **填价值公式**：

   | 项 | 要写什么 | 证据来源 |
   |---|---|---|
   | 新体验 | 具体增量：省时/省钱/降风险/增收入/情绪 | 原型测试、类比、试点 |
   | 旧体验 | 现状基线：耗时、步骤、错误率、覆盖率 | 访谈、观察、数据 |
   | 替换成本 | 学习、迁移、习惯、关系、风险、采购 | 访谈、迁移方案 |

   写成一句话：`用户从 [旧方案] 换到 [新方案]，得到 [增量]，付出 [替换成本]，净值为 [正/负/不确定]。`

2. **画交易结构**：

   ```
   谁供给 → 谁平台 → 谁付费 → 谁使用 → 谁受损
   ```

   平台型产品必须回答：补贴谁、向谁收费、哪一侧是稀缺侧、网络效应从哪来。

3. **算粗账**：单用户价值 × 可触达规模 vs 交付成本。数字可以粗，但必须写出来，并标注假设。

4. **写反证条件**：什么数据/事实出现，说明这个价值假设不成立。

### 提问脚本

- 「新体验的『新』，用一句话说是什么？用户能感知到吗？」
- 「用户现在这件事花多少时间/多少钱？你的方案省多少？」
- 「换过来要付出什么？谁承担？我们怎么帮他降低？」
- 「谁付钱？谁使用？如果付费方和使用方利益冲突，你站谁？」
- 「什么情况下，用户会放弃我们的方案？」

### 产出

价值假设表 + 交易图 + 反证条件。

### 示例（示意数字，非真实数据）

> 大学生复习笔记：旧方案是考前翻笔记 + 同学划重点，平均 40 分钟/次，覆盖率约 30%。
> 新方案是自动生成复习队列，3 分钟/次，覆盖率约 70%，预计记忆保持率 +15%。
> 替换成本：首次整理卡片约 15 分钟，学习新交互约 5 分钟。
> 净值：正，但前提是「首次整理 ≤ 15 分钟」；若超过 30 分钟，净值为负。
> 反证条件：若 7 日内卡片生成使用率 < 20%，说明「自动生成」没有解决整理成本。

### 常见错误

- 只算新体验，不算旧体验与替换成本。
- 把「用户说喜欢」当价值证据。
- 用 TAM/SAM/SOM 代替单用户价值。
- 忽略付费方与使用方的利益冲突。

### 退出检查

- [ ] 三项都有证据或明确标注为假设
- [ ] 能用一句话说清「用户为什么会换」
- [ ] 写出了反证条件
- [ ] 交易结构里没有「谁都不受损」的幻觉

## P3 建模：概念模型、信息架构、任务流

### 目的

让用户「一看就懂、一想就对」，并在动手画界面前暴露结构性问题。

### 动作

1. **画概念模型**：用用户熟悉的隐喻，定义四件事：

   | 要素 | 问题 | 示例（复习功能） |
   |---|---|---|
   | 对象 | 系统里有哪些「东西」？ | 笔记、卡片、复习计划、掌握度 |
   | 状态 | 每个对象有哪些状态？ | 新卡、学习中、待复习、已掌握 |
   | 动作 | 用户能对对象做什么？ | 生成、复习、评分、调整计划 |
   | 规则 | 状态如何流转？ | 评分 → 调整下次到期时间 |

   用一张图画出「对象-状态-动作」，不要用界面截图代替。

2. **七阶段走查**：

   | 阶段 | 用户问题 | 设计应答 |
   |---|---|---|
   | 目标 | 我想达成什么？ | 入口文案、价值主张 |
   | 意图 | 我该做什么？ | 主行动按钮、推荐下一步 |
   | 动作序列 | 具体怎么操作？ | 步骤、默认值、示例 |
   | 执行 | 我做得对吗？ | 即时校验、约束、预览 |
   | 感知 | 发生了什么？ | 状态变化、动效、提示 |
   | 解释 | 这意味着什么？ | 结果说明、对比、建议 |
   | 比较 | 达到目标了吗？ | 进度、完成度、下一步 |

3. **设计 IA**：按「对象-视图-动作」组织；菜单按任务分类，不按部门/技术分类。

4. **画任务流**：主流程 + 至少 3 条异常流（失败、超时、无权限、数据缺失、并发冲突）。

### 提问脚本

- 「用户会觉得这个系统像什么？他以前用过类似的东西吗？」
- 「第一次进来，他怎么知道下一步？如果不知道，界面上有什么？」
- 「操作完成后，他怎么知道成功了？失败了怎么办？」
- 「这条流程里，哪一步最容易出错？出错后能撤销吗？」
- 「异常情况下，谁处理？系统提示谁？」

### 产出

概念模型图 + IA 树 + 主/异常任务流。

### 常见错误

- 用页面清单代替概念模型。
- 把「系统架构」当「信息架构」。
- 只画正常流，异常流一句「提示错误」带过。
- 菜单按组织架构分，用户找不到任务。

### 退出检查

- [ ] 概念模型能用一张图讲清，且非设计人员能看懂
- [ ] 七阶段中没有「用户不知道下一步」的断点
- [ ] 异常流数量 ≥ 正常流的 1/3
- [ ] 纸面推演下，新用户能完成主任务

## P4 设计行为：行动、反馈、习惯（可选）

### 目的

让「第一次用」顺滑，让「下一次来」有理由；同时守住伦理边界。

### 动作

1. **B=MAT 拆解**：

   | 要素 | 问题 | 设计手段 |
   |---|---|---|
   | 动机 | 用户为什么现在做？ | 价值前置、损失厌恶（慎用）、社会证明 |
   | 能力 | 最大的摩擦是什么？ | 默认值、模板、批量、跳过、延后 |
   | 触发 | 什么时候提醒？ | 场景触发、事件触发、推送（慎用） |

   顺序：**先降能力门槛，再加动机，最后放触发**。动机最不稳定，能力最可控。

2. **设计反馈系统**：

   - 每个关键动作：即时、具体、可行动。
   - 提醒程度：静默（状态变化）→ 提示（toast/inline）→ 阻断（modal/拦截）。
   - 场景四问：谁需要知道？多快需要知道？不知道会怎样？知道了要做什么？

3. **判断是否做 Hook**：

   | 条件 | 是 | 否 |
   |---|---|---|
   | 高频（每周 ≥ 2 次） | 可做 | 不做 |
   | 价值可累积 | 可做 | 不做 |
   | 用户主动使用 | 可做 | 不做（强制流程不适合） |
   | 能通过伦理四问 | 可做 | 不做 |

4. **填 Hook 工作表**（仅当上述条件满足）：

   | 环节 | 内容 | 检验 |
   |---|---|---|
   | 内部触发 | 什么情绪/场景让用户想起产品？ | 不推送时用户会不会来？ |
   | 外部触发 | 冷启动期用什么提示？ | 能否逐步撤掉？ |
   | 行动 | 最小核心动作是什么？ | 30 秒内能否完成？ |
   | 可变奖励 | 哪一类（社交/猎物/自我）？ | 是否与核心价值相关？ |
   | 投入 | 用户留下什么？ | 是否让下次更容易且用户受益？ |

### 提问脚本

- 「用户不打开产品时，在逃避什么情绪？产品接住了吗？」
- 「第一次使用，30 秒内能得到什么？如果得不到，为什么？」
- 「最大的摩擦是时间、金钱、体力、脑力、社会压力，还是不符合习惯？」
- 「奖励是随机的，还是『不确定但相关』？两者差别很大。」
- 「用户投入后，是更离不开，还是更受益？两者能否同时成立？」

### 产出

核心交互流程 + 反馈矩阵 +（可选）Hook 工作表 + 伦理结论。

### 常见错误

- 用推送解决留存，用积分解决价值。
- 把「可变奖励」做成赌博。
- 对低频/B 端强制流程硬套 Hook。
- 反馈只有「成功/失败」，没有「下一步」。

### 退出检查

- [ ] 主路径每一步都有「下一步」和「结果感」
- [ ] 反馈可行动，而不只是告知
- [ ] 若用 Hook，通过伦理四问
- [ ] 若不用 Hook，写清了「为什么不用」

## P5 雕刻感知：留白、层级、感官

### 目的

让方案不仅「可用」，还「被记住、愿意靠近、显得可信」。

### 动作

1. **删**：列出可以删掉的 30% 信息、步骤、装饰。逐项问：删掉后任务还能完成吗？能，就删。

2. **立层级**：第一眼、第二眼、第三眼分别看到什么。一屏只允许一个「主角」。

3. **雕刻**：
   - 对比：大小、颜色、粗细、留白。
   - 节奏：分组、间距、重复、呼吸。
   - 文案：动词开头、具体、可执行；避免「赋能/抓手/闭环」。
   - 动效/声音：服务于状态变化，不服务于炫技。

4. **分场景**：
   - B 端：密度、扫描效率、批量操作、键盘流、异常可见性。
   - C 端：情绪曲线、峰值时刻、分享欲、回访理由。

### 提问脚本

- 「这个界面在『说』什么？一句话。」
- 「删掉一半，它还成立吗？删掉的是什么？」
- 「用户会记住哪一个瞬间？那个瞬间是设计出来的，还是碰巧的？」
- 「哪些元素是为了『显得高级』？它们解决了什么问题？」
- 「B 端用户一天看 200 次，这个设计还耐看吗？」

### 产出

3–5 条体验原则 + 关键界面的设计意图说明。

### 示例（体验原则）

1. **先给下一步，再给全貌**：首页只回答「现在该做什么」，完整数据退到第二层。
2. **默认即最佳实践**：所有可选项都有合理默认值，专家可改。
3. **异常比正常更显眼**：失败、超时、缺数据用固定位置与固定颜色，不藏在 toast 里。
4. **克制的奖励**：完成时给一次确认，不撒花、不弹窗、不打断。

### 常见错误

- 把留白当空洞，把克制当省略。
- 用视觉风格掩盖结构问题。
- B 端照搬 C 端的「大气」排版，牺牲密度。
- 文案写「系统提示」，不写「发生了什么、你该做什么」。

### 退出检查

- [ ] 每条原则都能指导一个具体取舍
- [ ] 第一眼层级清晰，且与任务一致
- [ ] 删减没有破坏可发现性
- [ ] B 端场景通过了「一天看 200 次」测试

## P6 验证：最小可信证据

### 目的

用最低成本证伪，而不是用最高成本证明自己是对的。

### 动作

1. **选验证方式**：

   | 假设类型 | 最低成本验证 | 样本 |
   |---|---|---|
   | 用户是否有这个问题 | 5–8 人访谈 | 代表性角色 |
   | 能不能看懂/做成 | 5 人可用性测试 | 目标角色 |
   | 愿不愿意用/付费 | 假门测试、预售、落地页 | 真实流量 |
   | 用了是否变好 | A/B 测试、灰度 | 统计功效 |

2. **建指标树**：

   ```
   北极星（任务成功/价值实现）
     ├── 行为指标（完成率、步骤数、时长、错误率）
     ├── 留存/效率指标（次日/周留存、人均处理量、培训时长）
     └── 商业指标（转化、续费、工单量、NPS）
   ```

3. **预注册放弃条件**：什么结果出现就改方案或停。写在验证计划里，避免事后解释。

### 提问脚本

- 「哪个假设一旦错了，整个方案就崩？」
- 「用什么最小实验能验证它？多久？多少钱？」
- 「什么结果会让你放弃？现在就写下来。」
- 「指标口径是什么？谁来埋点？什么时候能看？」

### 产出

验证计划 + 指标定义（口径、埋点、观察窗口）。

### 常见错误

- 用「用户说好」当验证。
- 指标太多，没有北极星。
- 事后改口径，把失败解释成成功。
- 可用性测试只找「友好用户」。

### 退出检查

- [ ] 每个关键假设都有验证动作
- [ ] 写下了放弃条件
- [ ] 指标能回答「任务是否完成」
- [ ] 验证成本与决策重要性匹配

## P7 交付与复盘

### 目的

让方案可被工程实现、可被评审、可被复盘。

### 动作

1. **写 PRD**（骨架）：

   ```
   1. 问题与目标（含非目标）
   2. 用户与场景（角色、任务、现状）
   3. 价值假设与成功指标
   4. 方案概述（概念模型图）
   5. 详细流程（主流程 + 异常流 + 状态机）
   6. 页面与交互说明（关键界面、反馈、空/错/加载态）
   7. 权限、数据、集成、非功能需求
   8. 埋点与指标口径
   9. 灰度、回滚、运营计划
   10. 风险与未决问题
   ```

2. **评审**：用 `assets/review-checklist.md`，按 CRITICAL / HIGH / MEDIUM / LOW 分级，给出「通过 / 有条件通过 / 不通过」。

3. **复盘**：上线 2–4 周后回填价值公式，对比预期与实际；区分「决策质量」与「结果质量」。

### 提问脚本

- 「上线后先看哪三个数？如果没达到，先改哪一层（价值/模型/行为/感知）？」
- 「最可能出问题的是哪一步？回滚方案是什么？」
- 「工程、设计、运营对『成功』的定义一致吗？」

### 产出

PRD + 评审记录 + 复盘结论。

### 常见错误

- PRD 只有正常流，没有异常与状态。
- 验收标准写「体验良好」，不可验证。
- 没有埋点，复盘靠感觉。
- 把「上线」当「完成」。

### 退出检查

- [ ] 工程能按 PRD 估时，无需口头补全
- [ ] 每个需求有可验证的验收标准
- [ ] 有埋点、有灰度、有回滚
- [ ] 三方对「成功」有同一个定义

## 完整案例：大学生笔记 App 的「每日复习」

> 以下数字均为示意，用于展示推演方式，不是真实数据。

### P0 问题陈述

> 大学生在考前复习时，想高效覆盖学过的笔记，但笔记分散、不知道哪些该复习、也估不准掌握程度，目前只能翻笔记、找同学划重点、考前突击。

非目标：不做社交、不做题库、不做老师端。
类型：C 端高频（考试周期内每日）。
为什么是现在：学生笔记已大量电子化，但复习仍靠人工筛选。

### P1 角色与场景

| 角色 | 场景 | 任务 | 现状替代 | 痛点 | 频率 |
|---|---|---|---|---|---|
| 学生 | 每晚自习结束 | 决定复习什么 | 翻笔记、凭感觉 | 不知道优先级 | 每天 |
| 学生 | 考前一周 | 快速过重点 | 同学划重点 | 覆盖不全 | 每学期 |
| 学生 | 上课后 | 整理笔记 | 手打/拍照 | 整理成本高 | 每周 |

断点排序：① 不知道复习什么（高频）② 整理成本高（高痛）③ 考前覆盖不全（高价值）。

### P2 价值假设

| 项 | 内容 | 证据等级 |
|---|---|---|
| 新体验 | 自动生成 3 分钟复习队列，覆盖率 70%，记忆保持 +15% | 假设 |
| 旧体验 | 40 分钟/次，覆盖率 30% | 访谈推断 |
| 替换成本 | 首次整理 15 分钟，学习 5 分钟 | 假设 |
| 净值 | 正，但依赖「首次整理 ≤ 15 分钟」 | 待验证 |

反证条件：7 日内卡片生成使用率 < 20%，或首次整理中位数 > 30 分钟。

### P3 概念模型

- 对象：笔记、卡片、复习计划、掌握度。
- 状态：新卡 → 学习中 → 待复习 → 已掌握。
- 动作：生成卡片、复习、评分（记得/模糊/忘了）、调整计划。
- 规则：评分决定下次到期时间；连续「记得」升级为已掌握。

七阶段走查（节选）：

| 阶段 | 风险 | 应答 |
|---|---|---|
| 目标 | 不知道为什么复习 | 首页显示「今天 12 张卡，预计 3 分钟」 |
| 意图 | 不知道从哪开始 | 一个主按钮「开始复习」 |
| 执行 | 不知道怎么评分 | 三个按钮 + 示例 + 可撤销 |
| 感知 | 不知道进度 | 顶部进度条 + 剩余张数 |
| 解释 | 不知道「模糊」意味着什么 | 「明天会再见」的说明 |
| 比较 | 不知道有没有变好 | 周报：掌握度变化 |

### P4 Hook（通过四问后启用）

| 环节 | 设计 | 检验 |
|---|---|---|
| 内部触发 | 考前焦虑、晚自习结束 | 不推送时是否有人主动打开？ |
| 外部触发 | 每晚 21:30 一条「今天 12 张卡」 | 可在设置中关闭 |
| 行动 | 3 分钟复习队列 | 30 秒内进入第一张卡 |
| 可变奖励 | 自我奖励（掌握感、连续天数） | 与核心价值相关，非赌博 |
| 投入 | 笔记、卡片、评分记录 | 让下次复习更准，用户受益 |

伦理四问：见 `references/03-heuristics.md`，结论为「可做，但需限制推送频率与连续天数文案」。

### P5 体验原则

1. 先给「今天做什么」，再给「全部笔记」。
2. 默认 3 分钟，可延长，但不主动加量。
3. 奖励克制：完成只给一次轻确认，不撒花。
4. 失败可撤销：误点评分可回退。

### P6 指标

- 北极星：周复习完成率（完成复习的用户 / 有到期卡片的用户）。
- 行为：首次生成耗时、单次复习时长、评分分布。
- 留存：次周回访率、考前 7 日活跃。
- 反证：生成使用率 < 20%，或完成率 < 30%。

### P7 交付要点

- 异常流：无笔记、卡片生成失败、离线、跨设备冲突。
- 埋点：生成、开始、完成、评分、撤销、推送点击。
- 灰度：先 5% 学生，观察 2 周。
