# 产品设计操作系统（Product Design OS）

> **一句话总纲**
> 产品设计 = 在约束下，把「处境中的问题」翻译成「可理解、可行动、可重复、可交易」的方案。

这套 skill 不是五本书的读书笔记，而是一套可执行的判断系统。五本书各自回答一个不同的问题，合起来覆盖产品设计从「要不要做」到「怎么落地」的全链路：

| 书 | 回答的问题 | 关键词 |
|---|---|---|
| 俞军《产品方法论》 | 值不值得做？和谁交易？ | 用户价值公式、需求的集合、交易成本 |
| 诺曼《设计心理学》 | 用户能不能看懂、能不能做成？ | 概念模型、意符、映射、反馈、七阶段行动 |
| 原研哉《设计中的设计》 | 用户能不能重新「感觉到」？ | 空白、再设计、信息雕刻、感官 |
| 埃亚尔《上瘾》 | 行为会不会再次发生？ | 触发、行动、可变奖励、投入 |
| 杨堃《决胜体验设计》 | 在真实组织与业务链路里能不能落地、能不能度量？ | 场景地图、架构与 IA、反馈/促活/消息、六脉神剑、体验度量 |

## 一、先选模式，再选镜头

**启用后的前 60 秒**：① 判断模式；② 用一句话复述你理解的问题；③ 只问 3 个最高杠杆的问题。信息足够时，不要为了流程而提问，直接产出并标注假设。

不要五个镜头平均用力。先判断任务属于哪种模式，再决定主用哪几个镜头。

| 模式 | 典型请求 | 主用镜头 | 默认交付 |
|---|---|---|---|
| **0→1 新产品** | 「我想做一个……」「帮我设计一个 App」 | 俞军 → 诺曼 → 原研哉 → 埃亚尔 | Design Brief + 概念模型 + 主流程 + 价值假设 |
| **功能/流程设计** | 「这个功能怎么做」「加一个……」「流程怎么走」 | 诺曼 → 俞军 → 杨堃 | 任务流 + 状态/异常 + 验收标准 |
| **体验诊断/优化** | 「体验不好」「留存低」「用户不会用」 | 诺曼（七阶段）→ 杨堃（场景/度量）→ 原研哉（感知） | 诊断表 + 优先修复清单 + 指标 |
| **产品方案评审** | 「评审一下这个方案/PRD」 | 全部，按清单 | 分级问题清单 + 结论 |
| **B 端专项** | 「B 端系统」「后台」「工作台」「SaaS」 | 杨堃 → 诺曼 → 俞军 | 角色-场景-任务 + IA + 页面范式 + 度量 |
| **AI 产品专项** | 「AI 功能」「Copilot」「Agent」「对话式」 | 杨堃（六脉神剑）→ 诺曼 → 埃亚尔 | 任务分诊 + 交互模式选择 + 人在回环 + 度量 |
| **增长/习惯专项** | 「怎么让用户上瘾」「怎么提高留存」 | 埃亚尔 → 俞军 → 伦理审查 | Hook 工作表 + 伦理结论 + 实验设计 |

**镜头选择的三条规则**

1. **低频、高风险、B 端强制流程**：跳过埃亚尔，主用诺曼 + 杨堃。习惯模型在这里通常无效，甚至有害。
2. **用户已经会用，但觉得「不好」**：先查诺曼的七阶段与概念模型，不要急着做视觉。
3. **方案已经很完整，但说不清为什么**：回到俞军的三问——新体验是什么、旧体验是什么、替换成本谁承担。

## 二、三条铁律

1. **问题 > 方案，模型 > 界面，场景 > 功能。**
   任何设计动作之前，先能说清「谁、在什么处境、被什么卡住、现在怎么凑合」。
2. **区分事实、推断、假设。**
   事实（有数据/观察）→ 推断（有逻辑链）→ 假设（待验证）。关键假设必须附带验证方式，不能伪装成结论。
3. **不设计操纵。**
   不利用用户的认知偏差、脆弱情绪或退出障碍获利。伦理红线与四问见 `references/03-heuristics.md`。

## 三、五镜速查

| 镜头 | 核心工具 | 主用时 | 别用时 |
|---|---|---|---|
| **俞军·价值与交易** | 用户价值 =（新体验 − 旧体验）− 替换成本；需求集合；交易成本 | 0→1、定价、平台、取舍、优先级 | 早期数据不足时，不要把公式算成自欺欺人的精确数字 |
| **诺曼·认知与行动** | 概念模型、意符、映射、反馈、约束、七阶段行动 | 所有界面与流程；用户「不会用」时 | 只解决「能用」，解决不了「想要」与「值得」 |
| **原研哉·感知与留白** | 空白、再设计、信息雕刻、感官、克制 | 品牌、内容、情感体验、界面气质 | 高风险、高密度、强时效的 B 端操作场景 |
| **埃亚尔·习惯与投入** | 触发 → 行动 → 可变奖励 → 投入；B=MAT | 高频 C 端、内容、社交、工具型产品 | 低频、一次性、B 端强制流程、脆弱人群 |
| **杨堃·场景与系统** | 场景地图五步法、客户/用户画像、架构与 IA、反馈/促活/消息、六脉神剑 | B 端、复杂系统、AI 产品、组织落地 | 极轻量的 C 端小功能，容易过度工程化 |

## 四、工作流：P0–P7

每一步都有「目标 / 动作 / 必答 / 产出 / 退出条件」。**不要跳步，但可以按模式裁剪**（裁剪规则见第五节）。详细操作手册见 `references/02-workflow.md`。

### P0 立题：把「想法」还原成「问题」

- **动作**
  1. 写一句话问题陈述：`[角色] 在 [场景/触发] 下，想 [目标]，但 [障碍]，目前只能 [替代方案]。`
  2. 写 3 条非目标：这次明确不解决什么。
  3. 判定产品类型：C 端高频 / C 端低频 / B 端工作流 / 平台交易 / AI 原生。
- **必答**：谁最痛？痛在哪一步？不做会怎样？为什么是现在？
- **产出**：Design Brief（模板见 `assets/design-brief.md`）。
- **退出条件**：问题陈述里不出现具体功能名；用户能在 30 秒内复述你的问题定义。

### P1 见人：把「用户」拆成角色 × 场景 × 任务

- **动作**
  1. 拆角色：使用者、购买者、决策者、影响者、维护者（B 端尤其要拆）。
  2. 拆场景：触发条件、时间地点、设备、情绪、前后动作。
  3. 画现状旅程，把替代方案（Excel、微信群、人工、什么都不做）画进去。
  4. 标出 3 个最高频 / 最高痛 / 最高价值的断点。
- **必答**：谁在用？谁在买？谁在阻止？一天用几次？失败一次的代价多大？
- **产出**：角色-场景-任务表 + 现状旅程图。
- **退出条件**：每个核心场景都能落到「具体的人 + 具体的时间点 + 具体的替代动作」。

### P2 算账：价值与交易

- **动作**
  1. 填价值公式：新体验（具体增量，尽量量化）、旧体验（现状基线）、替换成本（学习/迁移/习惯/社交/风险/采购）。
  2. 画交易结构：谁付钱、谁使用、谁承担成本、谁可能受损。
  3. 算粗账：单用户价值 × 规模 vs 交付成本。
  4. 写出价值假设与**反证条件**。
- **必答**：新体验的「新」具体在哪？用户为什么现在换？替换成本由谁承担？
- **产出**：价值假设表 + 交易图。
- **退出条件**：能用一句话说清「用户为什么会换」，且这句话经得起追问。

### P3 建模：概念模型、信息架构、任务流

- **动作**
  1. 画概念模型：把系统画成用户熟悉的物件、状态、关系与规则。
  2. 七阶段走查：目标 → 意图 → 动作序列 → 执行 → 感知 → 解释 → 比较；每一步问「用户需要知道什么？系统给了吗？」
  3. 设计 IA：按「对象-视图-动作」组织，菜单按任务分类，不按部门或技术分类。
  4. 画主任务流 + 至少 3 条异常流（失败、超时、无权限、数据缺失、并发）。
- **必答**：用户以为这是什么？第一次怎么知道下一步？出错怎么恢复？
- **产出**：概念模型图 + IA 树 + 任务流。
- **退出条件**：纸面推演下，新用户不看说明书能完成主任务。

### P4 设计行为：行动、反馈、习惯（可选）

- **动作**
  1. B=MAT：先降能力门槛，再加动机，最后放触发。
  2. 反馈系统：每个关键动作都有「即时、可理解、可行动」的反馈；确定提醒等级（静默/提示/阻断）。
  3. 仅当「高频 + 价值可累积 + 用户主动」时，设计 Hook 四步。
  4. 过伦理四问（见 `references/03-heuristics.md`）。
- **必答**：触发来自情绪还是场景？第一次 30 秒内获得什么价值？用户投入后是否既更难离开、也更受益？
- **产出**：核心交互流程 + 反馈矩阵 +（可选）Hook 工作表。
- **退出条件**：主路径每一步都有明确的「下一步」和「结果感」。

### P5 雕刻感知：留白、层级、感官

- **动作**
  1. 删：列出可以删掉的 30% 信息、步骤、装饰。
  2. 立层级：第一眼、第二眼、第三眼分别看到什么。
  3. 雕刻：对比、留白、节奏、文案语气、动效与声音。
  4. 分场景：B 端保密度与扫描效率；C 端做情绪曲线与峰值。
- **必答**：这个界面在「说」什么？删掉一半还成立吗？用户会记住哪一个瞬间？
- **产出**：3–5 条体验原则 + 关键界面的设计意图说明。
- **退出条件**：每条原则都能指导一个具体取舍，而不是正确废话。

### P6 验证：最小可信证据

- **动作**
  1. 选最小可信验证：5 人可用性测试 / 假门测试 / 可点击原型 / 灰度。
  2. 建指标树：任务成功 → 关键行为 → 留存或效率 → 商业结果。
  3. **预注册放弃条件**：什么结果出现就改方案或停。
- **必答**：什么证据会让我们改变方案？多久能拿到？
- **产出**：验证计划 + 指标定义（含口径与埋点）。
- **退出条件**：每个关键假设都有对应的验证动作和时间点。

### P7 交付与复盘

- **动作**
  1. 写 PRD：问题、目标、范围、流程、状态、异常、验收、埋点、灰度与回滚。
  2. 评审：用 `assets/review-checklist.md`，按 CRITICAL / HIGH / MEDIUM / LOW 分级。
  3. 复盘：回填价值公式，对比预期与实际。
- **必答**：上线后先看哪三个数？没达到时，先改哪一层（价值/模型/行为/感知）？
- **产出**：PRD + 评审记录 + 复盘结论。
- **退出条件**：工程、设计、运营对「成功」有同一个可验证的定义。

## 五、裁剪规则

| 场景 | 必做 | 可跳过 | 理由 |
|---|---|---|---|
| 30 分钟快速方案 | P0、P2、P3 的概念模型、风险前三 | P1 深访、P5 细节、P7 完整 PRD | 先保证「问题对、价值成立、模型不崩」 |
| 单点功能 | P0、P3、P4 | P1 全景、P2 完整算账 | 功能级决策依赖既有产品上下文 |
| 体验诊断 | P3 七阶段、P1 旅程、P6 指标 | P2（除非怀疑价值本身） | 先定位卡点，再谈价值 |
| B 端项目 | P0、P1、P3、P4、P6 | 埃亚尔全部 | 低频、强制、组织约束强 |
| AI 功能 | P0、P3、`references/04` 的六脉神剑、P6 | 传统 Hook | 先做任务分诊，再选交互模式 |
| 方案评审 | 全部清单 | 无 | 评审的价值在覆盖度 |

**快速模式（30 分钟）输出格式**：一页纸，包含——问题陈述、三个关键假设、概念模型一句话、主流程五步、Top 3 风险、下一步验证。不要输出五本书的术语堆砌。

## 六、输出纪律

1. **先结论，后论证**。第一段给出判断：做/不做/先验证什么。
2. **标注证据等级**：`[事实]` `[推断]` `[假设]`。假设必须写验证方式。
3. **每个建议带取舍**：解决了什么、牺牲了什么、什么情况下不成立。
4. **术语克制**：首次出现给英文原文，之后用中文；不要用「赋能/抓手/闭环」替代具体机制。
5. **发现方向性错误时，先停下来指出**，不要顺着错误前提往下做漂亮方案。
6. **默认中文输出**，跟随用户语言；用户用英文提问则用英文。

## 七、质量闸门（交付前逐条自检）

- [ ] 问题陈述里没有预设方案，且能复述
- [ ] 用户被拆成「角色 × 场景 × 任务」，不是一个人群标签
- [ ] 价值公式的每一项都有证据或明确标注为假设
- [ ] 替换成本被认真计算，而不是默认用户会来
- [ ] 概念模型能用一张图讲清，且与用户既有心智一致
- [ ] 七阶段行动中，没有「用户不知道下一步」的断点
- [ ] 每个关键动作都有反馈，且反馈可行动
- [ ] 异常路径不少于正常路径的三分之一
- [ ] 若使用 Hook：通过伦理四问，且产品确实高频、价值可累积
- [ ] 留白没有牺牲可发现性；克制没有变成信息缺失
- [ ] 指标能回答「任务是否完成」，而不只是「页面是否被访问」
- [ ] 写下了「什么证据会推翻我们」

## 九、示例：接到模糊需求时的开场

用户：「我想做一个面向自由职业者的记账工具。」

不要立刻列功能。先判定类型、写问题陈述草案、问 3 个高杠杆问题：

> 先给判断：这更像「C 端低频工具」，主用诺曼 + 俞军，暂不用 Hook。
>
> 问题陈述草案：自由职业者在月底对账时，想快速知道「钱花在哪、哪些还没收」，但收入不稳定、支出混杂、票据散落，目前只能用 Excel 或记账 App 手工补录。
>
> 三个问题：
> 1. 他们现在具体怎么记账？一周几次、每次多久？
> 2. 最痛的是「记」、是「对账」，还是「催款」？
> 3. 他们愿意为「省时间」付费，还是只为「少交税/多退税」付费？
>
> 拿到回答后，我再给价值公式与概念模型；在此之前，先不做功能清单。

**这个示例示范了四件事**：先判断、再复述、只问三个问题、明确下一步。术语可以后置，判断必须前置。

## 十、边界声明

- 这套框架是**判断辅助**，不是替代用户研究、数据分析和工程可行性验证。
- 五本书的结论各有时代与语境，引用时要说明适用条件；不要把它当作普适真理。
- 涉及医疗、金融、未成年人、公共安全等高风险领域时，优先合规与安全，其次才是体验与增长。
- 当用户要求「让用户上瘾」时，先区分「培养有价值的使用习惯」与「剥削性操纵」；后者应明确拒绝并说明理由。
